# 下一步优化方案（2026-08-26）

## 结论

下一轮应以 **详情页首开性能与稳定性** 为主线，而不是继续优化首页。

首页已经只加载 435 KB 的 `chars_index.json`，原来的 38 MB 全量字库启动问题已解决。现在的主要等待点移到了详情页：用户点开任一汉字时，需要解码一个 0.54–1.30 MB 的笔画分片；同时页面构建会无条件触发组词和中文释义两个整包 JSON 的读取与解析，共 4.90 MB。这样即使用户只想看笔顺动画，也会承担与该字无关的数据成本。

推荐的实施顺序如下：

1. 为详情页数据建立按字按需加载、可量化验证的分片链路。
2. 修正分片并发加载与几何缓存的边界问题，并补齐性能回归测试。
3. 在真实 Web CanvasKit 与 Android 设备上处理笔画交接的视觉问题。
4. 完成少量“已露出入口但尚未可用”的功能，并为发布建立基本闭环。

这条路线同时改善首次详情页体验、内存占用、稳定性和发布质量；不改变离线可用和完整字库覆盖的产品约束。

## P0：详情页按字分片与性能量化

### 目标

- 首页加载路径保持不变，不因为详情优化而变慢。
- 首次进入详情只读取“该字需要的笔画、组词和释义”分片，不解析全量 4.90 MB 参考数据。
- 资源切分的输出可重复生成、可验证，缺失时有明确失败态或可信降级。
- 用同一套 Web Chrome 与 Android release 基线验证结果，而不是只依赖主观体感。

### 设计

1. **将笔画分片从 256 字调为 64 字，并先做一次产物体积测量。**
   - `tools/split_chars_data.py` 已提供 `--shard-size` 参数，先以 64 生成候选产物，记录分片数、最大/中位/P95 文件大小和 Web 资源数。
   - 64 字通常会把当前单次 0.54–1.30 MB 的解码范围降为约四分之一，同时不会像“每字一个 JSON”那样造成大量资源与请求。
   - 若 Android / Web 资源清单或请求数出现明显回退，以 96 或 128 为备选；选择依据应是实测 P75 首开时间而非固定偏好。

2. **把组词与释义合并为同一套按字参考分片。**
   - 新建例如 `assets/data/references/reference_XXX.json` 的运行时产物，每片保存该段字符的 `{word, definition}` 数据；按与字库一致的 Unicode 排序和分片编号生成。
   - 在 `chars_index.json` 中复用或显式新增 `referenceShard` 映射，禁止在客户端扫描全部参考文件找字。
   - 用一个 `referenceForCharProvider(char)` 加载目标片，并仅向页面暴露该字的 `words` 和 `definition`。这样可消除两个独立整包读取和两次完整 `jsonDecode`。
   - `words.json`、`definitions_zh.json` 可以保留为构建中间产物和校验输入，但从 `pubspec.yaml` 的运行时 assets 移除；实际名称在实施时统一，以免双份资源误打包。

3. **延迟非核心模块的请求。**
   - 动画画布、基本信息先可用；参考数据分片独立显示加载态。
   - 若“汉字解释”或“组词举例”折叠，优先在展开时才 watch 对应数据；若产品坚持默认展开，仍只会读取目标分片。
   - 预取只限“当前字已经可见后”的下一次常见动作（例如用户切换到新详情页），不能抢占首屏。

4. **建立可复用的性能观测点。**
   - 在仓储层记录（debug/profile 构建）索引加载、分片读取、`jsonDecode`、首个 `StrokeCanvas` 完成绘制的耗时和对应资源字节数；release 默认关闭日志。
   - 使用固定样本集覆盖：小字（`一`）、常用中等笔画字（`火` / `母`）、高笔画字，以及当前观察字 `阳`。
   - 分别记录冷启动首页、首次详情、第二个同片字、第二个异片字、返回后再次打开的 P50/P75。没有这组基线，不应宣布具体毫秒级优化结论。

### 涉及文件

- `tools/split_chars_data.py`：调整笔画分片粒度与输出统计。
- `tools/build_words_dictionary.py`、`tools/build_definitions_zh.py`：保持原始生成职责；新增或调用统一的参考分片脚本。
- `lib/features/dictionary/data/asset_dictionary_repository.dart`：加载新的笔画分片契约。
- `lib/features/detail/application/reference_data.dart`：从“全量 map provider”改为“目标分片 provider”。
- `pubspec.yaml`、`docs/字库更新指南.md`：更新运行时资源与完整再生成命令。
- `test/reference_assets_validation_test.dart`、`test/dictionary_repository_test.dart`、`integration_test/e2e_test.dart`：验证每个样本字可解析、同片复用、异片加载、资源缺失和详情页降级。

### 验收标准

- 运行时不再加载或解析完整 `words.json` / `definitions_zh.json`。
- 每次首次详情加载只请求目标字所属的笔画/参考分片；同片第二字不会重复请求。
- 在确定测试设备与网络条件后，首次详情页的 P75 数据等待时间相对基线下降至少 50%，且首页 P75 不回退。
- 全量字库、6122 字组词、7451 字中文释义的覆盖契约仍通过；缺失条目显示明确占位，不崩溃、不显示伪造数据。
- Web Chrome、Android release 以及现有单元/组件/E2E 测试全部通过。

## P1：稳定性与渲染质量

### 1. 修复资源加载的并发语义

当前 `_loadShard` 用 `Set<int> _loadedShards` 做去重：第一个调用刚把编号放进集合、尚未完成读取时，第二个调用会立即返回；第二个调用可能因此看到只有元数据、没有 `strokes` 的 `CharacterEntry`。虽然现有 provider 通常会合并同一个订阅，这个仓储层行为仍不完整。

改为 `Map<int, Future<void>> _shardLoads`：同片并发调用共同 await 同一个 Future；成功后保留已加载标记，失败后移除该 Future，允许“重试”真正重新读取。`_ensureLoaded` 也用同样模式保存索引加载中的 Future，避免两个冷请求重复解析索引。

同时，将“分片缺失/损坏”从静默返回轻量条目改为可区分的状态：详情页显示“笔画资源加载失败，可重试”，而不是打开一个没有笔画的空画布。

验收：增加受控 `Completer` 的假 AssetBundle 测试，证明两个并发 `getByChar` 都拿到完整笔画、同片只读一次，失败后的第二次调用会重新加载。

### 2. 把名义 LRU 缓存修正为真实 LRU

`StrokeGeometryCache` 的注释称为 LRU，但当前 `Map` 只在写入时改变顺序，命中不会刷新访问顺序，因此实际是 FIFO。修复方式是在命中时将该项移除后重新插入，淘汰真正最久未访问的字；容量仍保持 16，避免无边界缓存 SVG `Path` 与笔刷 stamp。

实施时顺带检查缓存键：它目前只取首尾 SVG 的 `hashCode`。对于同字、中间笔画变更的测试数据，理论上可能复用陈旧几何。可以把完整笔画内容的稳定摘要纳入键，或在数据对象版本变化时显式清缓存；不要仅依赖 `hashCode` 的偶然唯一性。

### 3. 笔画交接处的视觉专项

已验证的约束：Web CanvasKit 中，跨笔 `Path.combine(union)` 会把“日”等字腔填掉。因此本项只允许“保持单笔原始路径”的方案。

建议按风险由低到高实验：

1. 调整未完成笔画的灰色明度/透明度，降低与黑笔相邻处的重量感；不改几何。
2. 仅在当前红笔的裁剪绘制中调整抗锯齿与覆盖，不让灰底的边缘反差放大。
3. 为 `阳`、`日`、`母`、`火` 等建立状态截图矩阵：未播放、交接瞬间、播放完成；同时在 Flutter 测试渲染和 Chrome CanvasKit 运行截图比对。

只要出现字腔填实、红黑断裂或跨引擎差异，即停止该候选方案并保留原始单笔路径。不要将多笔 Path 布尔运算重新引入生产路径。

## P2：小范围产品完成度提升

优先实现已经有 UI 入口、无需外部账号或高风险权限的能力：

- **分享**：Web 复制深链 / 系统分享可用时调用原生 share；不可用时明确提示“链接已复制”。深链格式沿用 `#/detail/<字>`。
- **田字格模式**：把现有占位按钮做成“田字格 / 米字格 / 无辅助线”的本地切换，状态写入设置而不是仅弹 SnackBar。
- **设置**：集中放置播放默认速度、自动播放、辅助线和亮度；先使用本地持久化，不引入账户体系。
- **拍照识字**：继续列为后续项目。它涉及相机权限、离线/在线 OCR 选型、儿童隐私说明和跨端能力，不宜混入本轮优化。

这些项目的验收原则是“入口可完成一个真实动作”。会员入口若没有明确业务定义，建议先隐藏，而不是继续保留占位提示。

## 本轮不建议做的事

- 不再重做首页索引或把中间字库文件移出仓库：两者对当前运行时瓶颈没有直接收益。
- 不用跨笔 `Path.combine` 合并灰影：已证实 Web CanvasKit 存在字腔错误。
- 不把相机 OCR、会员或账户系统混入性能迭代：它们会显著扩大权限、隐私和产品决策范围。
- 不在没有真实设备基线的情况下宣称固定的毫秒级提升；先量化，再用相对目标和实际样本验收。
